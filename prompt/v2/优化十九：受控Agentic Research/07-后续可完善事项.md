# 优化十九：后续可完善事项

记录日期：2026-09-26。本文只记录后续讨论点，不改变 00～06 的实施口径，也不表示下列事项已获准实施。

## 补证查询是否覆盖全部首轮缺失要点

**本次已确定的边界：**后端在 Research 响应的 `metadata.first_round_missing_aspect_ids` 返回首轮 Evidence Decider 判定的完整缺失要点 ID 集合，前端直接展示；补证任务继续展示各自绑定的 `aspect_ids`。最终 `evidence_pack.missing_aspects` 是 Finalizer 之后的状态，不能代替首轮缺失集合。Decider 降级时按 06 文档返回所有要点未确认覆盖，页面须注明这不是有效的证据判断。本次**不新增**“补证查询绑定的要点并集必须等于首轮全部缺失要点”的约束。

**待完善问题：**03 文档要求补证查询最多两个、只能绑定缺失要点，但没有明确要求所有缺失要点均被补证查询覆盖。当前后端只校验每条查询的绑定属于缺失集合，不校验绑定并集等于该集合。例如首轮缺失 `A2、A3`，仅生成绑定 `A3` 的 `Q4` 也可能被接受。这是允许的协议行为，不能仅凭这个现象认定模型能力不足；前端现在能够分别展示完整首轮缺失集合和实际补证覆盖范围。

将来如要改变规则，需先与用户确认：

1. 是要求尽量覆盖，还是强制所有缺失要点都被至少一条补证查询绑定？
2. 当缺失要点多于两个时，是否允许一个查询绑定多个要点，如何保证查询仍具定向性？
3. 如果模型只生成部分查询、查询重复或不合法，应重试、后端构造保底查询，还是保留部分补证并明确报告未覆盖要点？这些选择如何遵守现有超时、轮次和 LLM 调用上限？
4. 若确定新规则，补充到 06 后再调整 Decider 提示词、后端校验、接口展示和受控功能测试；不要仅在页面上把“已绑定要点”称为“全部缺失要点”。

上述属于后续产品和协议决策，不是本次功能验收或效果实验的通过条件。
