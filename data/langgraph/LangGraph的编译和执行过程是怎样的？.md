# LangGraph 的编译和执行过程是怎样的？

定义节点和边只是在描述图，还不能运行。必须调用 `compile()` 得到可执行对象，再用 `invoke`、`stream` 或 `stream_events` 真正执行。编译把开发时的图定义变成运行时的调度器，并挂上检查点、中断点等运行参数。

## 编译做了什么

编译会做结构检查，例如是否存在孤立节点、是否能从入口走到出口。同时在这里传入运行期依赖：checkpointer、store、静态断点等。官方明确说：使用前必须先编译。

```python
from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()
app = builder.compile(checkpointer=checkpointer)
```

编译通常只做一次。节点函数不会在编译时执行，所以编译很快。改了节点逻辑或边之后，需要重新编译，旧的编译结果不会自动更新。

把 checkpointer 放到 `compile()` 里，而不是 `invoke()` 里，是因为持久化属于这张图的运行配置。每次调用只要带上 `thread_id`，运行时就知道去哪读取检查点。

## 执行方式

最直接的是 `invoke(input, config)`，传入初始状态，阻塞直到图结束或遇到中断，返回输出状态。适合脚本和测试。

需要边运行边看中间结果时用流式接口。`stream` 可以按节点更新或按状态快照推送；`stream_events(..., version="v3")` 还能拿到模型 token、中断信息和子图事件。人机交互场景更适合事件流，因为它能明确告诉你这次是正常结束还是停在 `interrupt()`。

执行时通过 config 传入线程标识：

```python
config = {"configurable": {"thread_id": "ticket-42"}}
result = app.invoke({"email": "打印机连不上"}, config)
```

同一个 `thread_id` 会续上一次的检查点；换一个新 ID 就是全新会话。这和“再调用一次 compile”不是一回事。

## 超级步

运行时按超级步推进。可以并行的节点属于同一超级步，有先后依赖的节点属于不同超级步。检查点保存在超级步边界，而不是保存在节点函数的某一行。因此恢复执行时，出问题的节点会从函数开头重新跑，而不是从函数中间接着跑。编写节点时要默认自己可能被完整重放，副作用应尽量幂等。

## 应用场景

批处理脚本会在启动时编译一次图，然后对 100 封邮件循环 `invoke`，每封邮件用不同 `thread_id`。编译成本只付一次，执行阶段反复复用同一个 app 对象。如果把 `compile()` 写在循环内部，每次都重新检查图结构，既慢也没有额外收益。

开发时可以先不带 checkpointer 编译，确认节点逻辑正确；需要暂停恢复时再带上 checkpointer 重新编译。两份编译结果不要混用同一个存储。

## 容易混淆的边界

编译不是训练，也不是把图序列化成神经网络。它只是把 Python 对象变成可调度的运行时图，并做静态检查。

执行也不是“把所有节点按添加顺序跑一遍”。没有边相连的节点不会因为你先 `add_node` 就被执行。真正的顺序由边和超级步决定。

`compile()` 成功不代表业务逻辑正确。它主要抓图结构问题。节点里访问了不存在的状态键、工具抛错、模型超时，都要到执行阶段才会出现。要把编译错误和运行错误分开看：前者改图结构，后者改节点实现或错误策略。
